# PRD：Babel Core v2 多格式高性能核心

版本：1.0  
日期：2026-08-17  
关联上下文：`.omx/context/multiformat-high-performance-core-20260817T071429Z.md`

## 1. 产品承诺

Babel Tower 让个人译者在一个离线项目中持续翻译长文、严格映射的结构化单元和图片文字。用户只需要面对原文、译文和必要上下文；解包、解析、锚定、索引、校验、重打包、恢复和诊断由核心可靠完成。

核心的长期承诺不是“内置所有格式”，而是：任何受支持格式都必须进入同一套项目真相、译文覆层、身份绑定、任务调度和安全交付链路。新增格式不得另建译文数据库、另做保存模型或绕过导出验证。

## 2. 目标用户与关键任务

### 2.1 用户

- 个人文学与电子书译者。
- 业余汉化者和自由职业译者。
- 需要独立完成小型本地化交付的工作者。

### 2.2 首要任务

1. 导入作品并在短时间内看到第一批可翻译内容。
2. 在长文、单元、资源视图之间切换而不丢失当前位置和编辑状态。
3. 长时间输入、搜索、查前后文、维护术语与批注。
4. 安全保存并在崩溃或断电后恢复到明确状态。
5. 重新解析或升级格式支持时保留已有译文，并看见所有映射歧义。
6. 校验并导出与原作品基本一致、可验证且可追溯的交付文件。

## 3. 设计目标

### G1：一个项目真相

原始对象、项目单元、人工译文修订和绑定账本只有一个权威来源。视图、索引、OCR、缩略图、诊断和导出中间物都可重建。

### G2：格式扩展不重建核心

TXT、Markdown、EPUB、图片以及未来游戏表格、音频和视频通过版本化资源图、定位器和适配器契约进入同一系统。格式私有的往返信息可保留，但不能侵入编辑器公共模型。

### G3：人工译文不可静默丢失或错绑

任何重新抽取只能产生精确匹配、位置漂移、歧义或孤立四类显式结果。系统不得仅凭当前顺序把旧译文自动绑定给新单元。

### G4：交互优先

输入、耐久保存、当前上下文和视图切换拥有最高调度优先级。导入、OCR、重建索引和导出受资源治理，不得挤占交互预算。

### G5：离线可交付

每个平台各发布一个较大的完整离线产物：Windows 单一安装器包含 WebView2 Evergreen 离线安装器；Arch Linux 发布自包含 AppImage。产物包含核心、内置适配器、OCR 运行时与模型、必要字体/资源、许可证和完整性清单，不需要安装器联网、包管理器或命令行。断网情况下从安装、首次启动、导入到导出全链路可用。

### G6：性能可证伪

性能通过固定参考硬件、语料、测量方法和发布门禁定义。任何预算变更都需 ADR 和基准证据。

## 4. 非目标

- 不提供机器翻译、生成式 AI、自动润色或自动生成译文。
- 首版不开放任意第三方本机插件或稳定公开 ABI。
- 不把 TIR 建成覆盖所有文件语义的通用万能 AST。
- 不承诺首版完整编辑图片、音频或视频；首版资源能力聚焦图片 OCR、修正和基本嵌字。
- 不保证未知格式的无损导出；支持等级必须公开且由测试生成。
- 不追求云同步、多人协作或在线账号体系。
- 不以事件溯源或自研数据库取代简单可靠的本地权威存储。

## 5. 首版范围

### 5.1 必须完成

- 项目创建、导入、关闭、继续、备份与恢复。
- TXT、CommonMark 兼容 Markdown、EPUB 2/3 的抽取、编辑、校验和导出。
- Markdown/EPUB 内受支持图片的识别结果、人工译文、区域顺序和基本嵌字。
- 长文、单元、资源三种观察模式共享 `unit_id`、状态、撤销、搜索和进度。
- 文本段落和图片文字区域都呈现为同一种翻译工作项；格式差异只体现在结构保护、源定位、资源关联和导出规则。
- 资源模式支持按来源阅读顺序或当前筛选连续处理图片及图片内文字区域，不要求译者反复返回文件列表。
- 原译对照、前后文、项目历史译文检索、重复句、术语、人名地名一致性、批注、标记、查找替换和格式标记保护。
- 自动保存、显式耐久状态、崩溃恢复、失败任务隔离和本地诊断。
- 格式支持矩阵、导出前校验、导出记录、结果哈希和精确问题定位。
- Windows/Arch 各自以单一下载产物完成离线分发、首次安装/启动和升级迁移；只允许依赖版本化清单中声明的 Windows 内核/系统 DLL/API-set，或 Linux 内核/glibc/系统 ABI/图形会话基线，其他运行时必须随包提供。

### 5.2 预留但不在首版交付

- 游戏引擎资源包和表格/脚本适配器。
- 音频台词、时间轴字幕和视频画面文本。
- 受限第三方适配器 SDK 与签名分发。
- 高级图片修补、复杂字体拟合和专业排版。

## 6. 核心用户故事与验收标准

### US-01 导入大型作品

作为译者，我导入一个大型 EPUB 时，应在完整导入结束前看到已确认可翻译的内容，同时后台继续建立项目。

验收：

- 原文件先进入不可变对象库并记录 SHA-256，永不原地修改。
- 导入数据写入不可见的 `generation_id`；只有完整校验通过后才原子激活。
- 崩溃后旧激活代仍可打开；未完成代可恢复或安全清理。
- 首批内容和完整导入满足测试规范中的性能预算。

### US-02 跨视图连续工作

作为译者，我从长文切到单元或关联图片时，应仍然处理同一个翻译对象。

验收：

- 路由只改变观察方式，不重建项目会话。
- 当前 `unit_id`、选择范围、未提交输入和撤销组保持一致。
- 未提交输入由同一项目会话中的 `DraftSession` 持有；切换、断线或关闭时不覆盖已确认修订，恢复时按基准修订展示差异。
- 目标模式没有对应对象时给出明确的就地解释，不产生循环跳转。

补充验收：图片资源队列按稳定阅读顺序提供上一项/下一项；切换图片时保留当前项目会话、保存状态和筛选条件；当前图片内的区域按 `reading_order` 连续处理，关闭后可恢复到图片、区域和缩放位置。

### US-03 耐久保存与恢复

作为译者，我需要知道当前译文是否已经安全写入磁盘，并能从异常退出恢复。

验收：

- UI 的“已保存”只在 `synchronous=FULL` 事务确认后出现。
- 每个编辑命令有幂等 `command_id`，重放不会产生重复修订。
- 翻译修订追加保存，单元头是物化索引；缓存损坏不影响修订事实。
- 恢复界面使用用户语言解释候选状态，不暴露内部异常名。

### US-04 格式升级后保留译文

作为译者，我升级应用或重新导入更新后的源文件时，不希望译文被静默错配。

验收：

- 适配器和单元身份算法均有独立版本。
- 重新抽取生成绑定差异报告：`Exact`、`Shifted`、`Ambiguous`、`Orphaned`。
- 只有 `Exact` 可自动继承；`Shifted` 必须可审阅，另两类必须人工决定。
- 所有旧修订仍可访问，任何迁移可回滚到迁移前快照。

### US-05 安全导出

作为译者，我导出时希望得到能打开、结构有效并与当前译文一致的文件。

验收：

- 导出冻结一个 `commit_sequence`，后续输入不改变本次输出。
- 适配器先产生含前置哈希的声明式补丁计划，再写暂存输出。
- 输出通过格式结构、映射覆盖、危险遗漏和适配器专用验证后才原子发布。
- 导出失败不覆盖已有结果；导出记录保存输入快照、适配器版本、结果哈希和问题摘要。
- 发布意图先于文件发布写入；异常退出后系统能对账“已发布但记录未完成”的状态，不把未记录文件猜测为成功或失败。

### US-06 图片文字

作为译者，我可以识别图片区域、修正识别结果、写入人工译文并预览基本嵌字。

验收：

- OCR 结果和人工译文使用不同字段与状态。
- OCR 失败只影响对应派生任务，不影响文本译文和项目打开。
- 原图不可修改，衍生图进入对象库；导出引用明确选择的衍生版本。

### US-07 本地搜索与翻译辅助

作为译者，我能快速检索项目原文、译文、历史译文、术语和重复内容。

验收：

- 搜索索引可删除重建，不是权威事实。
- 单字、双字、标点、CJK、组合字符和大小写行为有固定测试。
- 搜索结果回到同一 `unit_id` 与上下文，不形成路由循环。

## 7. 格式支持等级

每个内置适配器必须在清单中声明并通过契约测试生成支持矩阵：

| 等级 | 含义 | 用户承诺 |
| --- | --- | --- |
| A | 精确保留未改内容，对已改区域做有界补丁 | 可用于正式交付 |
| B | 语义往返，可能发生已声明的规范化 | 导出前展示差异类别 |
| C | 仅抽取，不能安全回写 | 可翻译和保存项目，不允许正式导出 |
| U | 不支持 | 拒绝导入或仅作为不可编辑附件 |

首版最低目标：TXT A、受支持 Markdown A/B、符合支持子集的 EPUB 2/3 A/B、图片区域 B。具体子集由契约测试而不是营销文案决定。

## 8. 数据安全不变量

1. 源对象不可变，任何导出写入新路径。
2. 已确认人工译文只能由明确用户命令、可逆迁移或导入用户选择的数据改变。
3. 只有 SQLite 权威事务可推进 `commit_sequence`。
4. 派生缓存丢失不能导致人工译文丢失。
5. 数据库引用对象前，对象必须已完成写入、同步、校验和无覆盖发布。
6. 激活代只能指向完整且通过验证的资源图和绑定集合。
7. 适配器不能直接访问权威数据库或任意文件系统。
8. 导出候选未验证前不能替换已发布结果。

## 9. 性能产品预算

以下是首版发布门禁，不是当前完成声明。参考环境为 4 核 8 线程、16 GiB 内存、NVMe SSD 的 Windows 11/Arch Linux 机器。

| 场景 | 首版预算 |
| --- | --- |
| 输入到画面更新 | p95 ≤ 16.7 ms，p99 ≤ 33 ms |
| 当前单元耐久保存确认 | p95 ≤ 300 ms，p99 ≤ 750 ms |
| 热视图切换并定位当前单元 | p95 ≤ 100 ms |
| 冷视图切换 | p95 ≤ 250 ms |
| 可见页查询 | p95 ≤ 50 ms |
| 10 万单元搜索首屏 | p95 ≤ 150 ms |
| 已导入 10 万单元项目冷打开至可编辑 | p95 ≤ 3 s |
| 空闲 10 秒后的 CPU | ≤ 单个逻辑核的 1% |
| 10 万单元项目空闲 RSS（不含 OCR） | ≤ 400 MiB |
| 2 GiB 展开体积 EPUB 导入峰值 RSS（不含 OCR） | ≤ 1.5 GiB |

导入、导出和 OCR 的语料级预算、测量轮次及回归阈值见测试规范。

## 10. 发布成功标准

- TXT、Markdown、EPUB、图片适配器全部通过统一契约测试和恶意输入限制测试。
- Windows/Arch 断网端到端导入、翻译、异常恢复、校验、导出通过。
- 所有数据安全不变量通过故障注入证明。
- 参考语料上的交互、内存、导入和导出预算达标；未达标不得用降低持久性换取通过。
- 从任意派生缓存全删状态可恢复项目并重建到一致结果。
- 支持矩阵由适配器清单与测试结果生成，用户界面不宣称未验证能力。
- 首版安装包无需单独下载运行时、OCR 模型或格式组件。

## 11. 主要风险

- 格式“无损”承诺超过测试覆盖，造成导出损坏。
- 稳定身份设计不足，适配器升级后译文错绑。
- SQLite 长读事务或检查点策略不当，保存尾延迟恶化。
- Rust 异步执行、CPU 池和 OCR 进程分别扩容导致过度订阅与内存峰值。
- TIR 过于通用形成第二套文件格式，或过于贫乏导致每个适配器绕过核心。
- 过早开放插件 ABI，长期兼容债务压过产品迭代。

## 12. 待后续 ADR 决定

- CJK 搜索最终采用内置 tokenizer、trigram 还是受控自定义 tokenizer；必须先用真实语料比较体积、单字查询和更新成本。
- 对象库内部是否使用 BLAKE3 辅助指纹；外部持久身份仍用 SHA-256。
- OCR 模型组合、许可证和按平台加速后端。
- 公共第三方适配器 API 的开放门槛和签名分发机制。
