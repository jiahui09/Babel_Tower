# Babel Tower 多格式高性能核心：规划上下文快照

生成时间：2026-08-17 15:14（Asia/Shanghai）  
阶段：架构规划，尚未进入实现

## 1. 用户目标

设计一套从首版就能统筹 TXT、Markdown、EPUB 2/3、嵌入图片，并能继续扩展到游戏资源、音频台词和视频文本的离线桌面翻译核心。核心既要保护原件和人工译文，也要通过可量化的工程约束追求高性能，避免后续因格式扩展而重建权威存储、编辑模型或导出链路。

## 2. 已确认的产品边界

- 产品中心是“帮助人完成翻译”，不是项目管理、AI 翻译器或通用文本编辑器。
- 长文、单元、资源是同一翻译对象的三种观察方式；切换时保留当前 `unit_id`、上下文和撤销状态。
- 校验、恢复、诊断、任务和导出是交付保障能力，默认退居幕后。
- 首版目标平台为 Windows 与 Arch Linux，单个较大的完整离线安装包，无账号、无命令行、无联网依赖。
- 首版格式为 TXT、Markdown、EPUB 2/3，以及 Markdown/EPUB 中受支持的图片文字。
- 不集成机器翻译或生成式 AI。OCR 只产生“识别结果”，不能自动成为译文。
- 原始文件不可修改；扩展、崩溃、断电或导出失败都不能丢失已确认译文。
- 用户要求统一组件库和严谨的信息架构；本轮只规划核心架构，不实现前端。

## 3. 仓库事实

- `DESIGN.md` 已把产品收敛为“长篇人工翻译为核心、结构化资源与图片兼容”的个人翻译工作台。
- `TOOLCHAIN.md` 已选择 Tauri 2、React、TypeScript、Rust、SQLite 等首版技术栈。
- `.omx/plans/architecture-offline-translation-workbench.md` 已定义原件只读、SQLite 权威存储、对象库与独立工作进程等基础原则。
- 仓库当前没有应用源代码或依赖锁文件，无法做真实构建、性能基准或依赖审计。
- 当前工作树中 `DESIGN.md`、旧架构计划和 `TOOLCHAIN.md` 有既存未提交改动；本轮不得覆盖或回滚它们。

## 4. 本轮必须解决的问题

1. 什么才是跨格式的稳定内核，避免把 EPUB DOM、Markdown AST 或游戏表格结构写死进编辑器与数据库。
2. 哪些数据是权威事实，哪些只是可重建缓存。
3. 格式重新解析、适配器升级或源文件版本变化时，如何保留人工译文并显式处理映射歧义。
4. 如何让导入、OCR、校验、搜索和导出不阻塞输入、保存和视图切换。
5. 如何在单个离线安装包内隔离高风险解析器，同时不把插件生态变成首版产品形态。
6. 如何把“极致性能”变成可复现的预算、语料和发布门禁，而不是口号。

## 5. 外部工程证据

- SQLite WAL 允许读写并发但仍只有一个写者，因此适合单机权威控制面，前提是使用单写者、短事务、短读快照和受控检查点。
- SQLite `synchronous=FULL`、Backup API、STRICT 表和 FTS5 提供了持久性、备份、类型约束和本地搜索的基础能力。
- Git 的松散对象与 packfile 经验支持“内容寻址不可变对象 + 可回收压缩”的大对象存储模型。
- rustc 增量编译的查询指纹与投影思想表明，稳定、细粒度依赖键可显著减少无关失效。
- Protocol Buffers 的演进规则适合进程间控制协议；大对象仍应按句柄和哈希传递，避免序列化复制。
- Wasmtime/WASI Component Model 适合作为未来第三方适配器的能力隔离边界，但首版公开插件 ABI 会过早固化契约。
- EPUB 3.3、W3C EPUB Test Suite、CommonMark 与 Unicode UAX #29 可作为格式和文本边界的规范基线。

## 6. 规划决策摘要

采用“资源图—译文覆层内核” (`Babel Core v2`)：

- 不可变源对象平面：原件和大型衍生产物进入内容寻址对象库。
- 权威译文覆层：SQLite 保存项目身份、单元、人工译文修订、状态、术语、批注和命令结果。
- 绑定账本与资源图：稳定描述容器、文档、文本流、图片和未来时空资源之间的关系，并保存源锚点到项目单元的映射。
- 翻译中间表示 TIR：只表达翻译所需语义和受保护结构，不尝试成为所有格式的万能 AST。
- 持久化增量产物 DAG：解析、抽取、索引、缩略图、OCR、校验和导出计划均为可丢弃、可重建的派生结果。
- 受核心治理的内置适配器：首版使用原生工作进程；未来才通过 WIT/WASI 开放受限第三方扩展。
- 快照式安全导出：冻结提交序列、生成声明式补丁计划、写入暂存区、验证后原子发布。

## 7. 成功与停止条件

规划完成的条件：

- 架构计划、PRD 和测试规范互相引用且没有权威数据冲突。
- 明确格式适配器契约、稳定身份、重新映射、导入提交、任务调度、IPC、备份恢复和导出事务。
- 提供 Windows/Arch 可执行的格式契约测试、故障注入和性能门禁。
- 架构师先审查，评论员后审查，两者均给出 `APPROVE`。
- 仅生成规划产物，不修改产品源码，不宣称尚未基准验证的性能已实现。
